### Semana 1
- **Bitácora de prompts y cambios/ajustes:** Comencé solicitando una estructura desde cero para el comparador. Empezamos con un scraper en Python, pero ajustamos el enfoque a buscar metadatos estructurados (JSON-LD) para que el código no se rompa. Luego, inicializamos el frontend con React y Deno; descarté Streamlit por sus limitaciones visuales y aplicamos un diseño "Mobile First" limpio en CSS. Finalmente, implementamos el servidor backend con Deno y Hono para recibir la imagen desde el frontend, conectándolo a Azure Blob Storage para guardar las fotos de forma segura en la nube usando variables de entorno (.env).
- **¿Qué aprendiste?:** Aprendí que depender de las clases visuales de una web es frágil y es mejor extraer información de las etiquetas `<script type="application/ld+json">`. También aprendí a configurar un entorno React rápido con Vite. Adicionalmente, comprendí cómo comunicar cliente y servidor mediante peticiones HTTP (fetch y FormData), a optimizar costos en Azure eligiendo redundancia local (LRS), y a manejar permisos explícitos de ejecución en Deno.
- **¿Qué fue lo más difícil?:** Plantear una arquitectura que sea mantenible en el tiempo, resolver la codificación de caracteres en el scraper, y decidir el stack tecnológico. En la integración, lo más complejo fue entender el enrutamiento de peticiones POST (error 404), resolver problemas de caché eliminando la carpeta `node_modules`, y coordinar la ejecución simultánea de los servidores en distintas terminales.


### Semana 2 (Integración de IA y Puente Deno-Python)
- **Bitácora de prompts y cambios/ajustes:** El objetivo fue conectar el modelo de visión de Gemini 1.5 Flash al servidor Deno para analizar la etiqueta del perfume subida a Azure. Debido a errores 503 por alta demanda en los servidores de Google, implementamos un "Mock" (simulacro) temporal para no frenar el desarrollo. Luego, creé un puente usando `Deno.Command` para que el backend ejecute automáticamente el scraper de Python pasándole el nombre del perfume detectado, y finalmente actualizamos la interfaz de React para renderizar la tarjeta de precios.
- **¿Qué aprendiste?:** Aprendí a manejar fallos en servicios externos (APIs caídas) mediante la técnica de "Mocking", permitiendo que el frontend y el resto de la arquitectura sigan funcionando en desarrollo. También aprendí a ejecutar scripts de Python desde Deno de forma silenciosa, capturando su salida estándar (stdout) como JSON.
- **¿Qué fue lo más difícil?:** Lidiar con la saturación de los servidores gratuitos de IA, resolver el alcance (scope) de las variables dentro de los bloques `try/catch` en TypeScript, y silenciar los `print` de Python para no romper el parseo JSON en Deno.


### Semana 3 (Comparador Multifuente, Fichas de Fragancia, Historial y Reviews)
- **Bitácora de prompts y cambios/ajustes:** Implementamos la comparación de precios simultánea entre 3 fuentes chilenas reales en paralelo (Falabella con `__NEXT_DATA__`, Alisha Perfumes y Farmacias Ahumada). Creamos un endpoint para búsqueda directa por texto (`GET /api/buscar?q=...`) permitiendo comparar perfumes sin depender de una foto. Integramos IA generativa para confeccionar fichas olfativas con pirámide de notas (salida, corazón, fondo), concentración, duración y ocasiones. Desarrollamos un módulo de historial de precios con cálculo de variación porcentual y detección de tendencias, un componente de disponibilidad física y horarios por comuna, y un sistema comunitario para leer y publicar reviews con valoración por estrellas.
- **¿Qué aprendiste?:** Aprendí a orquestar múltiples scrapers en paralelo usando `ThreadPoolExecutor` en Python para reducir los tiempos de respuesta. Comprendí cómo persistir historiales temporales y opiniones comunitarias en formato JSON ligero, y cómo estructurar interfaces ricas en React para desplegar pirámides olfativas y gráficos de barras de precios nativos en CSS.

### Semana 5 (Stock Real, Historial Honesto, Horarios Scrapeados y Portabilidad)
- **Bitácora de prompts y cambios/ajustes:**
  1. **Portabilidad del proyecto entre equipos:** Al pasar el proyecto a otro computador los precios aparecían inventados y se perdían fotos. Pedí diagnosticar la causa: el scraper fallaba por falta de dependencias de Python y el backend rellenaba el historial con 3 precios calculados a partir de un valor fijo de $80.000; además todas las fotos eran URLs externas de CDN. Se eliminó ese relleno y se agregó la descarga local de imágenes (`backend/imagenes/`, ruta `GET /imagenes/:filename` y `POST /api/sync-imagenes`).
  2. **Limpieza de documentación:** Se quitaron los emojis de los archivos Markdown y se corrigieron datos desactualizados (URL de clonado, permiso `--allow-write` del backend, stack descrito como FastAPI cuando es Deno + Hono). Se eliminaron un archivo de contexto para IA que describía como pendientes funciones ya entregadas y el README de plantilla de Vite.
  3. **Verificación de stock real:** Al contrastar el proyecto con la rúbrica (punto 4: "scrapers para verificar stock") detectamos que las 4 tiendas devolvían `"En Stock"` fijo. Pedí inspeccionar en vivo qué señal de disponibilidad expone cada sitio antes de programar. Resultado: Falabella la publica solo en la ficha del producto (`isOutOfStock`, `isPurchaseable`), así que se consultan hasta 4 fichas en paralelo; DBS se detecta por el botón de carrito; Alisha por el campo `available` de su JSON de Shopify. Se definieron tres estados (`En Stock`, `Agotado`, `Sin verificar`) para nunca afirmar stock sin comprobarlo, y el mejor precio ignora las ofertas agotadas.
  4. **Recuperación de Alisha Perfumes y Farmacias Ahumada como fuentes:** Durante la inspección descubrimos que Alisha y Ahumada devolvían 0 resultados; en la práctica solo funcionaban 2 tiendas y la rúbrica exige al menos 3. Alisha renderiza su búsqueda con JavaScript, así que se migró al endpoint `/search/suggest.json` de Shopify, que entrega precio, imagen y disponibilidad. En Ahumada la primera hipótesis (también JavaScript) resultó equivocada: al probar con productos que la farmacia sí vende (Antonio Banderas, Shakira, Benetton) el HTML traía los productos, y el error era un selector `"a.link, .pdp-link a, a"` que tomaba el `<a>` vacío de la imagen. Se corrigieron los selectores y se agregó el stock según el botón "Agregar al Carrito". Ahumada no vende perfumes de diseñador como Sauvage o Acqua di Giò, por lo que en esas búsquedas no aparece.
  5. **Ofertas duplicadas:** En las pruebas en el navegador cada producto de DBS aparecía dos veces (el selector tomaba un `.product-item` y su copia anidada) y Falabella repetía productos patrocinados. Se filtraron los elementos anidados y los `skuId` repetidos.
  6. **Historial y descuentos honestos (dos iteraciones):** La ficha mostraba "-51%" comparando un frasco de 40 ml de Falabella con uno de 75 ml de DBS. En una primera iteración el historial pasó a guardar los ml y a comparar solo frascos del mismo tamaño, y se borraron de `historial_precios.json` los 3 puntos inventados que tenían los 32 perfumes. Al probarlo apareció otro caso engañoso ("-27%" entre un EDT de Falabella y un Parfum de DBS, ambos de 50 ml), así que se ajustó para comparar solo el mismo producto (tienda + nombre exacto) a lo largo del tiempo. También se agregó el tamaño en ml y el precio por ml en la ficha principal, porque costaba encontrar la cantidad del perfume.
  7. **Horarios de sucursales por scraping:** Los horarios estaban escritos a mano en el código. Se encontró el buscador oficial de locales de Farmacias Ahumada (`Stores-FindStores`), que devuelve en JSON 229 locales de la Región Metropolitana con horario por día, teléfono y coordenadas. Se creó `scraper_sucursales.py`; el backend lo ejecuta al iniciar con caché de 24 horas y, si falla, vuelve a la lista manual. La vista muestra las 12 sucursales más cercanas por GPS o por comuna e indica si el horario es "publicado por la tienda" o "referencial".
  8. **Corrección de codificación:** Los nombres con tilde (ej: "Acqua Di Giò") llegaban corruptos porque Python en Windows escribía la salida en otra codificación y Deno la leía como UTF-8. Ambos scrapers ahora emiten JSON en ASCII escapado.
  9. **Auditoría de datos inventados:** Pregunté si el historial, las fichas, las alergias y las recomendaciones eran reales. Al rastrear el origen de cada dato encontramos varios rellenos: el buscador por notas y el caché del navegador guardaban perfumes sin tienda con un precio por defecto de $79.990; 45 de los 88 perfumes indexados tenían notas por defecto (Bergamota, Madera y Ámbar) porque ninguna regla reconocía su nombre; sin IA disponible se generaba una ficha genérica para cualquier perfume; el comparador rellenaba con "~7h" o "Cítricos frescos" cuando faltaba un dato; y la grilla de productos relacionados mostraba un descuento calculado con la posición de la tarjeta. Se corrigió todo para mostrar solo datos verificables ("Sin datos", "Sin clasificar") y los relacionados ahora se eligen por familia, notas, marca y precio con el motivo visible. También se quitó Ambroxan de los alérgenos, porque no está en la lista de alérgenos que la normativa obliga a declarar, y se limitaron los alérgenos que devuelve la IA a los 8 conocidos.
  10. **Ofertas coherentes y precios que se actualizan solos:** Al probar, La Vie Est Belle mostraba "DBS, 100 ml" pero enlazaba a Falabella 75 ml. La causa eran varias mezclas de datos: la fusión del catálogo tomaba el precio de una oferta y la URL de otra; el backend y el crawler asumían 100 ml cuando no sabían el tamaño (50 perfumes tenían mal los ml, verificado abriendo sus fichas); al fusionar, ganaba la versión vieja guardada en el navegador; y cada búsqueda reemplazaba la oferta de un perfume por la más barata, que podía ser otro producto (La Vie Est Belle pasó a apuntar a La Vie Est Belle Elixir 30 ml). También se revisaron los 21 perfumes fijos contra Falabella: Valentino Uomo enlazaba a Born in Roma Uomo. Pregunté si había que buscar cada perfume para tener la información correcta, y se implementaron dos mecanismos: (a) al abrir un perfume del catálogo se muestra el precio indexado y en segundo plano se consultan las 4 tiendas, manteniendo activo el mismo producto; (b) el backend re-cotiza todo el catálogo una vez al día, solo cuando aparece el mismo producto (misma URL), y guarda un registro diario en el historial para detectar tendencias aunque nadie busque. El botón "Sincronizar tiendas", que antes borraba los perfumes aprendidos, ahora lanza este refresco. Para que las búsquedas y el refresco no se pisen, las escrituras de los JSON pasan por una cola (`utilidades.ts`, con tests).
- **¿Qué aprendiste?:** Aprendí a inspeccionar primero los datos reales de cada sitio antes de escribir el scraper, en lugar de suponer la estructura: así descubrí que dos de las cuatro tiendas no devolvían nada, que una búsqueda vacía puede significar que la tienda no vende el producto y no que el scraper esté roto (había que probar con productos que sí vende), y que muchos sitios exponen endpoints JSON internos (Shopify `suggest.json`, Salesforce `Stores-FindStores`) mucho más estables que el HTML. También aprendí que un dato honesto vale más que uno completo: es mejor mostrar "Sin verificar" o no mostrar un descuento que inventarlo, y que comparar precios exige comparar el mismo producto (tienda, tamaño y concentración). Además aprendí a probar el backend en una copia aislada en otro puerto para no interrumpir el servidor en uso, y a escribir tests con casos de disponible y agotado para los helpers de stock y horarios.
- **¿Qué fue lo más difícil?:** Detectar errores que no se ven en la consola sino en la interfaz: los descuentos engañosos solo aparecieron al revisar capturas reales de la aplicación, y la primera corrección (comparar por ml) no fue suficiente. También fue difícil que el scraping de stock no hiciera más lentas las búsquedas (se resolvió consultando las fichas de Falabella en paralelo con tiempo límite), y diagnosticar el problema de codificación entre Python y Deno en Windows, donde la consola mostraba caracteres rotos aunque los datos internos estuvieran bien.
