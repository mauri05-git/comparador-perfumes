### Semana 1
- **Bitácora de prompts y cambios/ajustes:** Comencé solicitando una estructura desde cero para el comparador. Empezamos con un scraper en Python, pero ajustamos el enfoque a buscar metadatos estructurados (JSON-LD) para que el código no se rompa. Luego, inicializamos el frontend con React y Deno; descarté Streamlit por sus limitaciones visuales y aplicamos un diseño "Mobile First" limpio en CSS. Finalmente, implementamos el servidor backend con Deno y Hono para recibir la imagen desde el frontend, conectándolo a Azure Blob Storage para guardar las fotos de forma segura en la nube usando variables de entorno (.env).
- **¿Qué aprendiste?:** Aprendí que depender de las clases visuales de una web es frágil y es mejor extraer información de las etiquetas `<script type="application/ld+json">`. También aprendí a configurar un entorno React rápido con Vite. Adicionalmente, comprendí cómo comunicar cliente y servidor mediante peticiones HTTP (fetch y FormData), a optimizar costos en Azure eligiendo redundancia local (LRS), y a manejar permisos explícitos de ejecución en Deno.
- **¿Qué fue lo más difícil?:** Plantear una arquitectura que sea mantenible en el tiempo, resolver la codificación de caracteres en el scraper, y decidir el stack tecnológico. En la integración, lo más complejo fue entender el enrutamiento de peticiones POST (error 404), resolver problemas de caché eliminando la carpeta `node_modules`, y coordinar la ejecución simultánea de los servidores en distintas terminales.


### Semana 2 (Integración de IA y Puente Deno-Python)
- **Bitácora de prompts y cambios/ajustes:** El objetivo fue conectar el modelo de visión de Gemini 1.5 Flash al servidor Deno para analizar la etiqueta del perfume subida a Azure. Debido a errores 503 por alta demanda en los servidores de Google, implementamos un "Mock" (simulacro) temporal para no frenar el desarrollo. Luego, creé un puente usando `Deno.Command` para que el backend ejecute automáticamente el scraper de Python pasándole el nombre del perfume detectado, y finalmente actualizamos la interfaz de React para renderizar la tarjeta de precios.
- **¿Qué aprendiste?:** Aprendí a manejar fallos en servicios externos (APIs caídas) mediante la técnica de "Mocking", permitiendo que el frontend y el resto de la arquitectura sigan funcionando en desarrollo. También aprendí a ejecutar scripts de Python desde Deno de forma silenciosa, capturando su salida estándar (stdout) como JSON.
- **¿Qué fue lo más difícil?:** Lidiar con la saturación de los servidores gratuitos de IA, resolver el alcance (scope) de las variables dentro de los bloques `try/catch` en TypeScript, y silenciar los `print` de Python para no romper el parseo JSON en Deno.


### Semana 3 (Comparador Multifuente, Fichas de Fragancia, Historial y Reviews)

Comprendí cómo persistir historiales temporales y opiniones comunitarias en formato JSON ligero, y cómo estructurar interfaces ricas en React para desplegar pirámides olfativas y gráficos de barras de precios nativos en CSS.

### Semana 5 (Stock Real, Historial Honesto, Horarios Scrapeados y Portabilidad)
- **Bitácora de prompts y cambios/ajustes:**
  1. **Portabilidad del proyecto entre equipos:** Al pasar el proyecto a otro computador los precios aparecían inventados y se perdían fotos. Pedí diagnosticar la causa: el scraper fallaba por falta de dependencias de Python y el backend rellenaba el historial con 3 precios calculados a partir de un valor fijo de $80.000; además todas las fotos eran URLs externas de CDN. Se eliminó ese relleno y se agregó la descarga local de imágenes (`backend/imagenes/`, ruta `GET /imagenes/:filename` y `POST /api/sync-imagenes`).
  2. **Limpieza de documentación:** Se quitaron los emojis de los archivos Markdown y se corrigieron datos desactualizados (URL de clonado, permiso `--allow-write` del backend, stack descrito como FastAPI cuando es Deno + Hono). Se eliminaron un archivo de contexto para IA que describía como pendientes funciones ya entregadas y el README de plantilla de Vite.
  3. **Verificación de stock real:** Al contrastar el proyecto con la rúbrica (punto 4: "scrapers para verificar stock") detectamos que las 4 tiendas devolvían `"En Stock"` fijo. Pedí inspeccionar en vivo qué señal de disponibilidad expone cada sitio antes de programar. Resultado: Falabella la publica solo en la ficha del producto (`isOutOfStock`, `isPurchaseable`), así que se consultan hasta 4 fichas en paralelo; DBS se detecta por el botón de carrito; Alisha por el campo `available` de su JSON de Shopify. Se definieron tres estados (`En Stock`, `Agotado`, `Sin verificar`) para nunca afirmar stock sin comprobarlo, y el mejor precio ignora las ofertas agotadas.
  4. **Recuperación de Alisha Perfumes y Farmacias Ahumada como fuentes:** Durante la inspección descubrimos que Alisha y Ahumada devolvían 0 resultados; en la práctica solo funcionaban 2 tiendas y la rúbrica exige al menos 3. Alisha renderiza su búsqueda con JavaScript, así que se migró al endpoint `/search/suggest.json` de Shopify, que entrega precio, imagen y disponibilidad. En Ahumada la primera hipótesis (también JavaScript) resultó equivocada: al probar con productos que la farmacia sí vende (Antonio Banderas, Shakira, Benetton) el HTML traía los productos, y el error era un selector `"a.link, .pdp-link a, a"` que tomaba el `<a>` vacío de la imagen. Se corrigieron los selectores y se agregó el stock según el botón "Agregar al Carrito". Ahumada no vende perfumes de diseñador como Sauvage o Acqua di Giò, por lo que en esas búsquedas no aparece.
  5. **Ofertas duplicadas:** En las pruebas en el navegador cada producto de DBS aparecía dos veces (el selector tomaba un `.product-item` y su copia anidada) y Falabella repetía productos patrocinados. Se filtraron los elementos anidados y los `skuId` repetidos.
  6. **Historial y descuentos honestos (dos iteraciones):** La ficha mostraba "-51%" comparando un frasco de 40 ml de Falabella con uno de 75 ml de DBS. En una primera iteración el historial pasó a guardar los ml y a comparar solo frascos del mismo tamaño, y se borraron de `historial_precios.json` los 3 puntos inventados que tenían los 32 perfumes. Al probarlo apareció otro caso engañoso ("-27%" entre un EDT de Falabella y un Parfum de DBS, ambos de 50 ml), así que se ajustó para comparar solo el mismo producto (tienda + nombre exacto) a lo largo del tiempo. También se agregó el tamaño en ml y el precio por ml en la ficha principal, porque costaba encontrar la cantidad del perfume.
  7. **Horarios de sucursales por scraping:** Los horarios estaban escritos a mano en el código. Se encontró el buscador oficial de locales de Farmacias Ahumada (`Stores-FindStores`), que devuelve en JSON 229 locales de la Región Metropolitana con horario por día, teléfono y coordenadas. Se creó `scraper_sucursales.py`; el backend lo ejecuta al iniciar con caché de 24 horas y, si falla, vuelve a la lista manual. La vista muestra las 12 sucursales más cercanas por GPS o por comuna e indica si el horario es "publicado por la tienda" o "referencial".
  8. **Corrección de codificación:** Los nombres con tilde (ej: "Acqua Di Giò") llegaban corruptos porque Python en Windows escribía la salida en otra codificación y Deno la leía como UTF-8. Ambos scrapers ahora emiten JSON en ASCII escapado.
  9. **Auditoría de datos inventados:** Pregunté si el historial, las fichas, las alergias y las recomendaciones eran reales. Al rastrear el origen de cada dato encontramos varios rellenos: el buscador por notas y el caché del navegador guardaban perfumes sin tienda con un precio por defecto de $79.990; 45 de los 88 perfumes indexados tenían notas por defecto (Bergamota, Madera y Ámbar) porque ninguna regla reconocía su nombre; sin IA disponible se generaba una ficha genérica para cualquier perfume; el comparador rellenaba con "~7h" o "Cítricos frescos" cuando faltaba un dato; y la grilla de productos relacionados mostraba un descuento calculado con la posición de la tarjeta. Se corrigió todo para mostrar solo datos verificables ("Sin datos", "Sin clasificar") y los relacionados ahora se eligen por familia, notas, marca y precio con el motivo visible. También se quitó Ambroxan de los alérgenos, porque no está en la lista de alérgenos que la normativa obliga a declarar, y se limitaron los alérgenos que devuelve la IA a los 8 conocidos.
  10. **Ofertas coherentes y precios que se actualizan solos:** Al probar, La Vie Est Belle mostraba "DBS, 100 ml" pero enlazaba a Falabella 75 ml. La causa eran varias mezclas de datos: la fusión del catálogo tomaba el precio de una oferta y la URL de otra; el backend y el crawler asumían 100 ml cuando no sabían el tamaño (50 perfumes tenían mal los ml, verificado abriendo sus fichas); al fusionar, ganaba la versión vieja guardada en el navegador; y cada búsqueda reemplazaba la oferta de un perfume por la más barata, que podía ser otro producto (La Vie Est Belle pasó a apuntar a La Vie Est Belle Elixir 30 ml). También se revisaron los 21 perfumes fijos contra Falabella: Valentino Uomo enlazaba a Born in Roma Uomo. Pregunté si había que buscar cada perfume para tener la información correcta, y se implementaron dos mecanismos: (a) al abrir un perfume del catálogo se muestra el precio indexado y en segundo plano se consultan las 4 tiendas, manteniendo activo el mismo producto; (b) el backend re-cotiza todo el catálogo una vez al día, solo cuando aparece el mismo producto (misma URL), y guarda un registro diario en el historial para detectar tendencias aunque nadie busque. El botón "Sincronizar tiendas", que antes borraba los perfumes aprendidos, ahora lanza este refresco. Para que las búsquedas y el refresco no se pisen, las escrituras de los JSON pasan por una cola (`utilidades.ts`, con tests). Para saber cuándo termina el refresco se agregó un indicador en la barra superior ("Actualizando precios 34/93" con barra de avance, luego "Precios al día" con fecha y hora) que consulta `GET /api/refresco`; al terminar, el catálogo se recarga solo. El primer refresco real revisó 93 perfumes y re-cotizó 46; en los otros 47 el mismo producto no apareció entre los primeros resultados de la búsqueda, así que conservaron su precio anterior con su fecha.
  11. **Comparador más honesto y simple:** El veredicto comercial declaraba "Acqua di Giò es más económico, ahorras 42%" comparando un frasco de 50 ml con uno de 100 ml. Ahora, con el mismo tamaño compara el precio total, con tamaños distintos compara el precio por ml y muestra ambos valores ("19% menos por ml: $1.200/ml vs $1.480/ml"), y si falta el tamaño dice "Precio no comparable" en vez de elegir un ganador. También se quitaron los 100 ml y las ~7 h que se asumían cuando faltaba el dato. Para que la vista sea más directa, la tabla resumen va antes del radar, y las ofertas que antes no se podían elegir (solo se mostraban 4) quedan en un "Ver N ofertas más".
  12. **"Para ti" en la página principal:** Pedí que la portada recomendara según las preferencias del usuario. Sin login, se usan las señales que la app ya guarda en el navegador: la lista de compras (Favorito pesa más que Por comprar; Regalo no cuenta porque es para otra persona), las búsquedas recientes y las alergias. Con los perfumes que le gustan se calculan sus familias, notas y rango de precio, y se puntúa el resto del catálogo; solo se recomienda si comparte familia o notas, se excluyen sus alérgenos y cada tarjeta explica el motivo ("Como Bad Boy: misma familia (ámbar), notas de madera y vainilla"). La lógica está en `paraTi.ts` con su test (`node tests/paraTi.test.ts`). Al probarlo apareció otro dato inventado: un usuario nuevo veía "Acqua Di Gio, Sauvage Dior, Good Girl" como búsquedas recientes por defecto, y "Para ti" recomendaba según búsquedas que nadie hizo; ahora se parte vacío.
  13. **Re-cotización directa por URL:** En el refresco diario, 47 de 93 perfumes conservaban un precio viejo porque el mismo producto no aparecía entre los primeros resultados de la búsqueda. Como el catálogo ya guarda la URL exacta de cada oferta, ahora, si la búsqueda no lo trae, se lee directamente la página del producto: el JSON `__NEXT_DATA__` en Falabella, la etiqueta `product:price:amount` en DBS y el endpoint `.js` de Shopify en Alisha (que entrega el precio en centavos). En la prueba con 16 perfumes se actualizaron los 16, 4 de ellos desde su página, y Polo Blue bajó de $39.990 a $36.900, un cambio que antes se perdía. La ficha que se abre desde el catálogo usa lo mismo (`GET /api/cotizar`). Como Falabella nombra distinto al mismo producto en la búsqueda ("EDP 90ml - GIORGIO ARMANI") y en su página ("Eau De Parfum 90Ml Giorgio Armani"), el historial ahora guarda también la URL y reconoce el mismo producto por URL y tamaño, para no partir su serie de precios en dos. Tests nuevos en `test_scraper_stock.py`.
  14. **Comparador más útil:** El título de cada columna usa la concentración de la oferta elegida (antes decía "EDP" por defecto aunque fuera un EDT); cada oferta muestra su precio por ml y si está agotada; el tamaño se lee también desde la URL cuando el nombre no lo trae; y cuando los dos frascos elegidos son de tamaños distintos pero ambos perfumes se venden en uno común aparece el botón "Comparar ambos en 100 ml", que elige la oferta más barata disponible de ese tamaño en cada lado.
  15. **Pantallas chicas:** Revisé la app a 375 px (celular) y 768 px (tablet) buscando elementos que se salieran de la pantalla. Se corrigió la barra de pestañas superior, que se cortaba a la izquierda; las columnas del comparador, que se salían por la derecha (faltaba `minmax(0, 1fr)` en la grilla); las pestañas de la ficha, que se desordenaban en varias filas y ahora se deslizan en una sola; el catálogo, que mostraba una tarjeta por pantalla y ahora usa 2 columnas; y el encabezado, que en celular ocupaba media pantalla (se ocultan la descripción y los textos de los botones, que conservan su nombre accesible). Además, las ventanas emergentes ahora se cierran con Escape y se anuncian como diálogos.
  16. **Alergias según el envase y notas de la tienda:** Al revisar qué publica cada tienda encontramos que Falabella incluye en la ficha del producto la lista oficial de ingredientes (INCI) y, a veces, las notas aromáticas. Como la app ya abría esa página para el stock, ahora se guardan sin hacer consultas extra. Con la lista de ingredientes, los alérgenos se leen de lo que declara el fabricante en vez de estimarlos por las notas (`alergenosEnIngredientes` en `utilidades.ts`, con test; "Hexyl Cinnamal" no se confunde con "Cinnamal"). En My Way, la estimación por notas encontraba 4 alérgenos y el envase declara 6, entre ellos cinnamal, eugenol y citral, que son de riesgo alto o moderado. El semáforo indica de dónde sale el dato ("declarados en la lista de ingredientes del envase" o "estimados a partir de las notas"), y la ficha muestra las notas que publica la tienda y la lista completa de ingredientes. Los datos se guardan por oferta para no mezclar productos distintos de una misma búsqueda. También se conectó Azure OpenAI (gpt-4o) como primera opción para la ficha olfativa; la suscripción de estudiante solo tenía cuota en regiones que su política no permitía, y se resolvió creando el recurso en South Africa North. Gemini queda de respaldo.
  17. **Ingredientes con función y cantidad aproximada:** Un botón "Ver ingredientes y cantidades" en la ficha (con el resumen "17 ingredientes · 10 alérgenos declarados") abre una ventana con la lista del envase ordenada en tres partes: una barra de composición aproximada (alcohol, aroma, agua y el resto), los alérgenos declarados como etiquetas y los demás componentes con su función (filtro UV, colorante o estabilizante). El envase no trae porcentajes, así que la cantidad se deduce de dos reglas de etiquetado (los ingredientes van de mayor a menor cantidad y los alérgenos se declaran sobre 0,001 %) y del rango típico de concentrado de cada tipo: 15–20 % en un Eau de Parfum, 5–15 % en un Eau de Toilette. La ventana aclara que son rangos típicos y no valores medidos. Se llegó a este diseño probándolo: primero fue un desplegable dentro del recuadro de precio, que el usuario no encontró, y luego una lista de 17 filas con barras casi iguales, que costaba leer. Si la oferta abierta no trae la lista, el botón cambia a la oferta que sí la tiene. Al probar con Bad Boy se corrigieron tres lecturas: el nombre del producto entre asteriscos que la tienda antepone, "Alpha-Isomethyl Ionone" (alérgeno) y un "Alcohol" repetido más abajo, que ya no recibe el rango de la base. Al probar con My Way Ylang se corrigieron dos lecturas: "Alcohol de anís" es un alérgeno y no la base de alcohol, y "En 19140 / Año 5" es un colorante mal traducido por la tienda. Algunas fichas de Falabella (Acqua di Giò) publican la lista sin comas ("Alcohol Aqua / Agua Perfume / Fragancia Bht Linalol…"); en ese caso se separa reconociendo los nombres INCI conocidos, y solo si reconoce casi todas las palabras, para no partir una descripción libre. También se agregó la forma en español "Linalol", que el semáforo de alergias no reconocía. Si la tienda pone una descripción en vez de una lista, se muestra el texto tal cual (`leerIngredientes` en `frontend/src/ingredientes.ts`, con test).
  18. **Semáforo honesto y base de listas conocidas:** Este es el problema de fondo del proyecto: la caja de un perfume siempre trae su lista de ingredientes, pero casi ninguna tienda la publica (de 97 productos de Falabella revisados, solo 34 tenían una lista completa, y DBS, Alisha y Ahumada no tienen ese campo). Al revisarlo descubrimos que la app decía "Compatible con tu Perfil Dermatológico" en verde cuando no encontraba los alérgenos del usuario en las notas olfativas, sin haber visto la lista real; para una persona alérgica es el error más grave posible, porque compuestos como linalool o limonene están en casi todos los perfumes y no se notan en la pirámide. Se cambiaron tres cosas:
      - **Semáforo:** el verde solo aparece cuando la lista del envase confirma que el alérgeno no está. Sin lista, el aviso dice "Sin verificar para tu perfil" y pide revisar la caja; las alertas estimadas dicen "podría contener" en vez de "contiene", y el catálogo, el quiz y "Para ti" dicen "sin tus alérgenos en sus notas" en vez de "compatible". En el comparador, si un perfume declara su lista y el otro solo se estima, el veredicto dermatológico es "No comparable todavía" (una lista real declara más compuestos que una estimación, y contarlos juntos premiaba al que no declara).
      - **Listas resumidas:** algunos vendedores escriben solo "Alcohol - Parfum - Aqua". Antes eso contaba como "0 alérgenos declarados" y volvía a dar verde, aunque la caja real de Light Blue declara limonene, linalool y citral. Ahora una lista con solo alcohol, aroma y agua no cuenta como declaración.
      - **Base de listas conocidas (`ingredientes_conocidos.json`):** cada lista completa que aparece al buscar, al abrir una ficha o en el refresco diario se guarda. Si otra oferta no publica la suya, se usa la del mismo perfume en la misma concentración (misma fórmula, otro tamaño o tienda), y la ficha dice de dónde se tomó. La identidad de la fórmula (`claveFormula`/`mismaFormula` en `utilidades.ts`, con test) ignora tamaño, orden de las palabras y marca faltante, pero distingue versiones ("My Way" de "My Way Ylang"), concentraciones (EDT de EDP) y género ("Hombre"/"Mujer"); ante la duda no reusa nada, para fallar hacia "sin lista" y nunca hacia una lista equivocada. Con la base también se calcula en cuántos perfumes conocidos aparece cada alérgeno (`GET /api/ingredientes/frecuencias`), dato que el aviso "Sin verificar" muestra como contexto. La base se sembró leyendo las 97 páginas de Falabella del catálogo: quedaron 34 listas completas de 27 fórmulas identificables, y limonene y linalool aparecen en las 27 (citral en 23, geraniol en 24, coumarin en 16, eugenol en 14 y cinnamal en 8). Ese dato confirma por qué el verde por notas era peligroso. En la prueba, las ofertas de Alisha de My Way Ylang (que no publica ingredientes) recibieron la lista del envase publicada por Falabella para el mismo perfume.
  19. **Los 26 alérgenos de la norma europea:** La lista del envase puede declarar hasta 26 alérgenos de fragancia (Reglamento europeo 1223/2009), pero "Mis Alergias" solo permitía elegir 8: alguien alérgico al salicilato de bencilo o al hidroxicitronelal nunca recibía aviso, aunque el envase lo declarara. Además había cuatro listas de alérgenos distintas (dos en el backend, una en el semáforo y una en el lector de ingredientes), por eso el botón decía "16 alérgenos declarados" y el semáforo "6 compuestos". Ahora hay una sola lista con los 26 (`frontend/src/alergenos.ts`, con test), que usan el backend, el semáforo y el lector. En "Mis Alergias" los 9 más frecuentes siguen como tarjetas y los otros 17 aparecen como botones compactos. Eugenol e isoeugenol, y geraniol y citronellol, antes eran un solo alérgeno y ahora están separados; quien ya tenía marcado eugenol o geraniol recibe también isoeugenol o citronellol, para no perder avisos. Con la lista completa, la base muestra que en los 27 perfumes conocidos el salicilato de bencilo y la alfa-isometil ionona aparecen en 20, el alcohol bencílico en 18 y el hidroxicitronelal en 15, y que uno declara Lilial, prohibido en la Unión Europea desde 2022.
  20. **Perfumes sin foto:** En "Para ti" algunos perfumes de DBS aparecían sin foto. DBS carga las fotos al hacer scroll: en el atributo `src` deja un GIF transparente y la foto real va en `data-src` y `srcset`, y el indexador leía primero `src`. Había 39 entradas con el GIF guardado como imagen (19 en `catalogo_descubiertos.json` y 20 en `catalogo_knasta.json`). Se agregó `url_imagen` en `scraper_stock.py` (con test), que prefiere `data-src`, `data-original` o `srcset` y descarta los `data:`, y se usa en los cuatro lugares donde los scrapers leen una foto; las 39 entradas se repararon con la foto de la página de cada producto (`og:image`). Después apareció otro caso: las fotos que el backend guarda en `backend/imagenes` no cargaban si la página se abría antes de que el backend terminara de arrancar, y el navegador no las volvía a pedir, así que se veía el nombre del perfume en lugar de la foto. Ahora `main.tsx` reintenta esas fotos cada 2,5 segundos (hasta 4 veces) y oculta las que no cargan en vez de mostrar su texto.
  21. **Ficha más clara:** En las pruebas el usuario dijo que la ficha era poco intuitiva, y al revisarla con My Way se corrigieron cinco cosas. El título usaba el nombre de la ficha aunque la oferta abierta fuera otra versión: abriendo "My Way Ylang" de Alisha decía "My Way"; ahora agrega la versión que trae la oferta, o usa el nombre de la oferta si es otro perfume (`nombreSegunOferta` en `frontend/src/nombres.ts`, con test). Los botones de las ofertas no decían el tamaño ("Alisha: $43.990" y "Alisha: $69.990" se veían iguales); ahora dicen "Alisha · 30 ml · $43.990" y muestran el nombre completo al pasar el cursor. El aviso de alergias aparecía dos veces (arriba y dentro de la pestaña Características) y la descripción también (en la pestaña y en un resumen debajo); ahora cada uno aparece una vez. La pirámide repetía notas entre niveles porque el catálogo partía las notas con cortes que se solapaban; ahora se reparten en tercios, la pirámide muestra cada nota una sola vez y oculta los niveles vacíos, y la IA recibe la instrucción de no repetirlas. Por último, la ficha abría en "Todas las Tiendas", que era la última pestaña; ahora es la primera.
  22. **Ficha según la oferta abierta:** La ficha (notas, radar, guía y semáforo) era del perfume buscado aunque la oferta abierta fuera otro: buscando "My Way", la primera oferta era "Maison Azhar Your Way", de otra marca, y mostraba la pirámide de My Way. Ahora `esMismoPerfume` (en `frontend/src/nombres.ts`, con test) decide si la oferta es el perfume de la ficha: tiene que traer su nombre sin palabras de versión, la marca cuando es parte del nombre ("Bleu de Chanel" no calza con "Iris Bleu" de Armani) y no el género contrario (Light Blue de mujer y de hombre son perfumes distintos). Las variantes como "My Way Ylang" cuentan como otro perfume, con el mismo criterio de la base de listas: en la duda, ninguna ficha antes que una equivocada. Para otro perfume, las pestañas Características y Guía avisan "Esta oferta es X" con un botón para buscar su ficha, y el semáforo no desaparece: usa solo la lista de ingredientes de esa oferta o queda "Sin verificar", sin estimar con las notas del perfume buscado.
  23. **Comparador más claro:** Al revisar el comparador con Acqua di Gio vs Sauvage aparecieron tres problemas. El selector de oferta estaba al final de cada columna, debajo de la pirámide, y al cambiar de oferta los veredictos cambiaban arriba, fuera de la vista; ahora van primero las dos tarjetas con su precio y selector, después los veredictos y la tabla, luego el radar y al final las notas de cada perfume. Los textos usaban jerga ("Laboratorio Comparativo Multi-Tienda & IFRA", "Opción A · Índigo", "Ejecutar Duelo Comparativo", "Arquitectura de Acordes"); ahora dicen "Compara dos perfumes", "Perfume A", "Comparar", y los veredictos son "Precio", "Duración" y "Para tu piel" con el nombre de la oferta elegida. El veredicto de piel decía "Sauvage es más suave" por tener menos compuestos regulados, lo que premiaba al que no declara su lista; ahora habla de los alérgenos del usuario: cuál los declara en su envase, cuál podría tenerlos según sus notas, y "Sin verificar" cuando falta la lista de alguno (`veredictoPiel` en `frontend/src/veredictoPiel.ts`, con test). Sin alergias configuradas, ofrece configurarlas.
  24. **Elegir perfumes sin escribirlos:** Al probar el comparador noté que para comparar perfumes que ya tenía guardados había que escribir su nombre de nuevo. Ahora, al hacer clic en el buscador principal o en los campos del comparador, se despliega una lista con lo guardado en "Mi Lista" (separado en por comprar, favoritos y para regalar, con tienda, tamaño y precio), las búsquedas recientes y, en el comparador, los populares; al escribir, la lista se filtra, y se puede elegir con el mouse o con las flechas y Enter (`CampoPerfume` en `frontend/src/components/CampoPerfume.tsx`). La lista guarda el nombre que usa la tienda ("Perfume Hombre Acqua Di Gio EDT 50ml - GIORGIO ARMANI"), así que al elegirlo se busca como "Giorgio Armani Acqua di Gio" (`terminoDeBusqueda` en `frontend/src/nombres.ts`, con test). Reemplaza los botones de nombres rápidos que había bajo cada campo del comparador.
- **¿Qué aprendiste?:** Aprendí a inspeccionar primero los datos reales de cada sitio antes de escribir el scraper, en lugar de suponer la estructura: así descubrí que dos de las cuatro tiendas no devolvían nada, que una búsqueda vacía puede significar que la tienda no vende el producto y no que el scraper esté roto (había que probar con productos que sí vende), y que muchos sitios exponen endpoints JSON internos (Shopify `suggest.json`, Salesforce `Stores-FindStores`) mucho más estables que el HTML. También aprendí que un dato honesto vale más que uno completo: es mejor mostrar "Sin verificar" o no mostrar un descuento que inventarlo, y que comparar precios exige comparar el mismo producto (tienda, tamaño y concentración). Además aprendí a probar el backend en una copia aislada en otro puerto para no interrumpir el servidor en uso, y a escribir tests con casos de disponible y agotado para los helpers de stock y horarios. Con las alergias aprendí que la mayoría de las tiendas no publica la lista de ingredientes, que las notas de la pirámide no revelan compuestos como el linalool o el limoneno (aparecen en 64 de las 66 listas conocidas), y que por eso el semáforo no puede decir "Compatible" sin la lista del envase: deducir de perfumes conocidos sirve solo para el mismo perfume y concentración, y en la duda es mejor no mostrar una lista que mostrar una equivocada.
- **¿Qué fue lo más difícil?:** Detectar errores que no se ven en la consola sino en la interfaz: los descuentos engañosos solo aparecieron al revisar capturas reales de la aplicación, y la primera corrección (comparar por ml) no fue suficiente. También fue difícil que el scraping de stock no hiciera más lentas las búsquedas (se resolvió consultando las fichas de Falabella en paralelo con tiempo límite), y diagnosticar el problema de codificación entre Python y Deno en Windows, donde la consola mostraba caracteres rotos aunque los datos internos estuvieran bien. Lo último más difícil fue que la interfaz fuera intuitiva: varias funciones existían pero no se encontraban (la lista de ingredientes, el selector de oferta del comparador), y solo lo noté al probar la aplicación tratando de encontrarlas.

### Semana 6 (Etiquetas que Funcionan, Búsqueda Tolerante a Errores, Resultados por Partes y Rediseño "Almacén de Campo")
- **Bitácora de prompts y cambios/ajustes:**
  1. **Prueba con un usuario que sabe de perfumes:** Le mostré la aplicación a un amigo que conoce de perfumes y, según me dijo, la pudo usar mejor que yo. De esa prueba salieron los problemas de esta semana: los filtros por etiquetas no servían, la búsqueda no perdonaba errores al escribir, seguía lenta, y un perfume nuevo que buscamos no tenía ficha.
  2. **Etiquetas que funcionan:** Pedí revisar por qué los filtros por notas no discriminaban. El diagnóstico: había tres copias de la lista de etiquetas (frontend, backend y crawler) que buscaban pedazos de palabra en la descripción y en el nombre del perfume, así que "rosa" salía de "poderosa", "menta" de "experimenta" y "coco" de "Coco Mademoiselle"; en el catálogo descubierto 70 de 104 perfumes tenían "Madera" y 67 "Bergamota". Además solo se guardaban las 6 primeras notas (las de fondo nunca), la ocasión era siempre "Oficina & Diario" y 45 de los 88 perfumes del catálogo indexado no tenían ninguna etiqueta. Ahora hay una sola lista (`frontend/src/etiquetas.ts`, con test) que usan el backend y el frontend: compara palabras completas, solo de las notas y acordes, distingue "pimienta rosa" y "palo de rosa" de la flor, la familia es la que la ficha nombra primero (y "Sin clasificar" si ninguna calza, en vez de "Amaderado" por defecto), se guardan todas las notas y un perfume puede tener varias ocasiones. Cada búsqueda re-etiqueta el perfume en el catálogo, y `deno run -A --env server.ts --etiquetar` re-etiqueta el catálogo completo. Al re-etiquetar todo apareció un segundo problema: aun con las notas bien leídas, "Madera", "Jazmín" y "Bergamota" quedaban en 3 de cada 4 perfumes, porque casi todos llevan algo de cedro, jazmín, bergamota y almizcle; el filtro seguía sin separar. Por eso las etiquetas ahora salen de los acordes principales de la ficha (a qué huele sobre todo) y las notas sueltas solo cuentan para las que definen a un perfume aunque sean una entre varias (chocolate, café, tabaco o cuero, caramelo o miel, notas marinas) (`etiquetasDePerfume`). Resultado sobre los 104 perfumes distintos del catálogo: la etiqueta más común bajó de 76 % a 56 %, la mayoría tiene 3 o 4 etiquetas, y 14 fichas de lanzamientos recientes se armaron con la descripción de las tiendas. Ocho perfumes que la IA no conoce y cuyas tiendas no publican notas quedaron sin ficha.
  3. **Búsqueda tolerante a errores de tipeo:** "savage dior" o "versache eroz" no devolvían nada (lo comprobé contra las tiendas: 0 resultados después de 5 a 10 segundos). Ahora la consulta se corrige contra los perfumes que la aplicación ya conoce (`corregirBusqueda` en `frontend/src/busquedaFlexible.ts`, con test): solo propone un cambio si todas las palabras calzan con un mismo perfume conocido, para no "corregir" el nombre de un perfume nuevo. La pantalla avisa "Mostrando resultados de …" y deja buscar lo escrito tal cual. Si la corrección no lo conoce y ninguna tienda lo encuentra, se busca de nuevo por el nombre oficial que reconoce la IA. Los filtros del catálogo y la lista de perfumes guardados también aceptan errores y palabras a medio escribir.
  4. **Resultados por partes:** Medí dónde se iba el tiempo: la búsqueda esperaba a la tienda más lenta (DBS tarda entre 4 y 16 segundos; Falabella y Alisha, 1 a 2) y además a la IA (unos 6 segundos, a veces 20). Ahora `/api/buscar-vivo` entrega las ofertas de cada tienda apenas responde y la ficha cuando está lista: en las pruebas las primeras ofertas aparecen a los 2 a 2,5 segundos en vez de 6 a 8. La ficha de cada perfume se guarda en disco (`fichas_conocidas.json`) y la IA se consulta una sola vez por perfume, también para el comparador.
  5. **Perfumes que la IA no conoce:** El perfume nuevo sin ficha tenía una causa concreta: la IA no conoce los lanzamientos posteriores a su fecha de corte y respondía "no es un perfume" (pasó con My Way Ylang y Power Of You). Al pedirle que identificara el perfume igual, lo sustituía por otro de la marca ("Power Of You" por "Stronger With You"), lo que es peor que no tener ficha porque cambia las notas y los alérgenos. Quedó así: si las tiendas venden el nombre buscado y la IA describe un perfume con otro nombre, esa ficha se descarta (`nombresDistintos`, con test); y cuando la IA no lo conoce, la ficha se arma con la descripción que publica la tienda (Alisha incluye las notas) y se muestra el aviso "esta ficha se armó con la descripción que publican las tiendas". Si ninguna tienda publica notas, el perfume queda sin ficha en vez de con una inventada. También se limpió el término que se busca cuando el nombre viene del título de una tienda ("… Set de Regalo 3 Piezas … + 150 ml Desodorante").

  16. **Cuentas de usuario propias:** Para las cuentas había elegido Supabase, pero al ver todo lo que implicaba pregunté si había algo más simple. Supabase resolvía dos cosas: el login y dónde guardar los datos al publicar la aplicación (Render gratis borra los archivos al reiniciar). Elegí la alternativa más simple: publicar en Railway con un disco, donde los archivos JSON siguen funcionando, y un login propio. El login está en `backend/cuentas.ts` (con `cuentas_test.ts`) y no usa librerías: la contraseña se guarda derivada con PBKDF2-SHA256 de 600.000 iteraciones (lo que recomienda OWASP; medido en 0,25 s) y una sal aleatoria por usuario; la sesión es un token aleatorio en una cookie `HttpOnly` y `SameSite=Lax`, y en disco solo queda su SHA-256, así que cerrar sesión la invalida de verdad. Los intentos fallidos se limitan por correo y por IP (5 cada 15 minutos), un correo inexistente tarda lo mismo que uno real, y los cambios solo se aceptan desde la propia aplicación. Para que el navegador envíe la cookie se cambió CORS, que aceptaba cualquier origen, por una lista de orígenes permitidos. Lo probé atacándolo: otro origen no recibe permiso, una cookie inventada o la de una sesión cerrada no sirven, una cuenta no ve los datos de otra, se rechazan enlaces `javascript:` y al sexto intento fallido se bloquea. La cuenta es opcional: al entrar, Mi Lista y las alergias del navegador se suman a la cuenta y cada cambio se guarda en ella; al cerrar sesión se borran del navegador, por si el equipo es compartido. Los archivos de cuentas quedaron fuera de git antes de crearlos. No hay recuperación de contraseña, porque requeriría enviar correos.
